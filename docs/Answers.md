Ответы на контрольные вопросы
1. Что такое обмен сообщениями (messaging) и какие проблемы в архитектуре ПО он решает?

Обмен сообщениями — это способ взаимодействия компонентов системы через передачу сообщений посредником (брокером), а не напрямую. Решает проблемы: слабая связанность (сервисы не знают друг о друге), асинхронность (отправитель не ждёт получателя), масштабируемость (можно добавить потребителей), устойчивость к сбоям (сообщения сохраняются в очереди).

2. Что такое брокер сообщений? Какова его роль в системе?

Брокер сообщений — это промежуточное ПО, которое принимает сообщения от издателей, хранит их в очередях и передаёт потребителям. Роль: маршрутизация, буферизация, гарантия доставки, развязка компонентов.

3. Перечислите и охарактеризуйте основные шаблоны обмена сообщениями.

Point-to-point (очередь): сообщение получает один потребитель.

Publish/Subscribe (тема): сообщение получают все подписчики.

Request/Reply: запрос-ответ через очереди.

Work Queues: несколько worker'ов делят задачи из одной очереди.

4. Дайте определение RabbitMQ.

RabbitMQ — это open-source брокер сообщений, реализующий протокол AMQP. Написан на Erlang, поддерживает очереди, exchanges, маршрутизацию, подтверждения, кластеризацию.

5. Какой протокол лежит в основе RabbitMQ?

AMQP 0-9-1 (Advanced Message Queuing Protocol). Также поддерживает MQTT, STOMP, AMQP 1.0 через плагины.

6. В RabbitMQ сообщения, принятые от приложения-продюсера, записываются …

… в очереди (queues). Но перед этим проходят через exchange (точку обмена), который маршрутизирует их в одну или несколько очередей по правилам binding.

7. Объясните, что такое точка обмена (exchange).

Exchange — это сущность в RabbitMQ, куда издатель публикует сообщение. Exchange по правилам (тип + binding + routing key) решает, в какие очереди направить сообщение.

8. Что такое Binding в RabbitMQ?

Binding — это правило связи между exchange и очередью. Определяет, какие сообщения из exchange попадут в эту очередь. Может содержать routing key.

9. Дайте определение Routing Key в RabbitMQ.

Routing key — это строка-ключ, которую издатель указывает при публикации. Exchange использует её вместе с binding, чтобы решить, в какие очереди направить сообщение.

10. Опишите по шагам процесс маршрутизации сообщения в RabbitMQ (от продюсера до потребителя).

Продюсер подключается к брокеру.

Публикует сообщение в exchange с указанием routing key.

Exchange по своему типу и bindings решает, в какие очереди направить.

Сообщение попадает в очередь (или в несколько).

Потребитель, подписанный на очередь, получает сообщение.

Потребитель отправляет ack (подтверждение).

Брокер удаляет сообщение из очереди.

11. Если необходимо просто распараллелить обработку сообщений, принятых от продюсера, по нескольким потребителям, какой тип обменника надо выбрать?

Достаточно default exchange (пустая строка "") — маршрутизация по имени очереди. Несколько потребителей на одной очереди → задачи распределяются round-robin. Тип exchange здесь не важен, подойдёт и direct.

12. Какие типы точек обмена (exchanges) существуют в RabbitMQ и в чём их принципиальные отличия?

direct — по точному совпадению routing key и binding key.

fanout — рассылка во все привязанные очереди, routing key игнорируется.

topic — маршрутизация по шаблону (* — одно слово, # — ноль или более).

headers — маршрутизация по заголовкам сообщения, а не по routing key.

13. Обычно приложение-продюсер, отправляя сообщение в RabbitMQ, отправляет его …

… в exchange (точку обмена), а не напрямую в очередь.

14. Как предотвратить потребление устаревших данных из RabbitMQ?

Установить TTL (time-to-live) для сообщений или очереди.

Использовать очереди с лимитом (x-max-length) — старые вытесняются новыми.

Настроить Dead Letter Exchange для «просроченных» сообщений.

Использовать consumer prefetch и актуальность данных на стороне потребителя.

15. По какому принципу LIFO или FIFO устроены очереди в RabbitMQ?

Очереди RabbitMQ работают по принципу FIFO — первым пришло, первым ушло. При нескольких потребителях — round-robin. Исключение — Priority Queue, где сообщения с более высоким приоритетом обрабатываются раньше.

16. Для чего предназначен Server (Broker/Node) в RabbitMQ.

Server (Broker/Node) — это сам процесс RabbitMQ, который принимает соединения, хранит очереди и exchanges, маршрутизирует сообщения, управляет подписками и подтверждениями. Несколько нод могут объединяться в кластер.

17. Опишите назначение Virtual Host (Vhost) в RabbitMQ.

Vhost — это логическая изоляция внутри одного брокера. У каждого vhost свои exchanges, queues, users, permissions. Позволяет разделять окружения (dev/prod) или разных клиентов на одном RabbitMQ.

18. Что такое подтверждение сообщений (acknowledgments / ack, nack, reject) и зачем оно необходимо?

Подтверждение — сигнал от потребителя брокеру, что сообщение обработано (ack) или не обработано (nack/reject). Нужно для гарантии доставки: если потребитель упал до ack, сообщение вернётся в очередь и будет передано другому.

ack — успешно обработано.

nack — не обработано (можно вернуть в очередь).

reject — отклонено (без возможности вернуть).

19. Чем отличаются долговечные (durable) и временные (transient) очереди и сообщения? Как это влияет на перезагрузку брокера?

durable (очередь) — сохраняется после перезапуска брокера.

transient — удаляется при перезапуске.

persistent (сообщение) — сохраняется на диск, переживёт перезапуск.

transient — потеряется при перезапуске.

Для полной сохранности нужны: durable queue + persistent message.

20. Что такое Dead Letter Exchange (DLX) и какие сценарии его использования?

DLX — это exchange, куда попадают сообщения, которые не были доставлены/обработаны:

отклонены (nack/reject без requeue),

просрочены (TTL),

превышен лимит очереди.

Сценарии: обработка ошибок, отложенные задачи, аудит «мёртвых» сообщений, повторная обработка.

21. Что такое Priority Queue в RabbitMQ и как она работает?

Priority Queue — очередь, где сообщения с более высоким приоритетом обрабатываются раньше. При объявлении задаётся x-max-priority (0–255). Публикуя сообщение, указывают priority. Работает не идеально точно, но эффективно для срочных задач.

22. Дайте определение Apache Kafka. Какие основные задачи она решает и чем её философия отличается от классических брокеров?

Kafka — распределённая потоковая платформа для публикации, хранения и обработки потоков событий. Основные задачи: шина событий, потоковая обработка, лог-агрегация, интеграция систем. Философия: сообщения не удаляются после прочтения, а хранятся определённое время (log-based), потребители сами читают из топика и управляют своим offset'ом.

23. Опишите архитектуру Kafka. Что такое Broker, Topic и Partition?

Broker — сервер Kafka, хранит партиции топиков.

Topic — логическая категория сообщений.

Partition — упорядоченная часть топика; внутри партиции сообщения строго упорядочены. Топик делится на партиции для параллелизма и масштабирования.

24. Что такое Consumer Group (группа потребителей) и как она влияет на масштабирование и распараллеливание чтения?

Consumer Group — группа потребителей, которые совместно читают топик. Каждая партиция топика читается ровно одним потребителем в группе. Это позволяет масштабировать чтение: больше потребителей → больше партиций обрабатывается параллельно.

25. Что такое реплика (Replica)? Чем роль Leader отличается от роли Follower?

Реплика — копия партиции на другом брокере. Leader обрабатывает все чтения и записи. Follower синхронизируется с Leader'ом и подхватывает его роль при отказе. Репликация обеспечивает отказоустойчивость.

26. Что такое ZooKeeper (или подсистема KRaft в новых версиях) и какова его роль в архитектуре Kafka?

ZooKeeper — координационный сервис, который хранил метаданные кластера Kafka (список брокеров, партиций, лидеров). В новых версиях Kafka (2.8+) внедрён KRaft — встроенный консенсус-протокол на основе Raft, который убирает зависимость от ZooKeeper и упрощает архитектуру.

27. Что такое Kafka Streams и как он отличается от написания Consumer-приложений?

Kafka Streams — библиотека для потоковой обработки данных прямо в Kafka (фильтрация, агрегация, join, окна). Отличие: при написании consumer-приложения ты вручную управляешь offset'ами, состоянием и обработкой. Kafka Streams берёт это на себя, предоставляя высокоуровневый DSL.

28. В чём заключаются фундаментальные архитектурные отличия между RabbitMQ и Apache Kafka?

RabbitMQ	Kafka
Модель	Очереди, push	Лог, pull
Хранение	До прочтения	После прочтения (по времени/размеру)
Маршрутизация	Exchange + binding	Топик + partition
Состояние	Сообщение удаляется после ack	Хранится, offset у потребителя
Порядок	В очереди	В партиции
Масштабирование	Много потребителей на очередь	Partition = единица параллелизма
29. Приведи примеры, в каких сценариях предпочтительнее использовать RabbitMQ, а в каких — Apache Kafka.

RabbitMQ: RPC, очереди задач с подтверждениями, сложная маршрутизация (topic/direct/headers), высокая вариативность приоритетов, интеграция legacy-систем.

Kafka: потоковая обработка в реальном времени, event sourcing, log aggregation, аналитика, большие объёмы данных, воспроизведение событий (replay).

30. Можно ли использовать RabbitMQ и Apache Kafka в одной архитектуре? Если да, то за какие зоны ответственности каждый из них будет отвечать?

Да, можно. Типичное разделение:

Kafka — шина событий и потоковая аналитика (что произошло в системе), долговременное хранение.

RabbitMQ — операционные задачи, RPC, очереди заданий, маршрутизация с гибкими правилами, доставка с подтверждениями.
